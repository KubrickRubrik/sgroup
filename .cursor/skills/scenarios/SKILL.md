# /scenarios — Схема сценария

Уточнить границы сценария коротким гриллингом, затем записать sequence-схему в Markdown. Код фичи не менять.

Форма вопросов — как в [grilling/SKILL.md](../grilling/SKILL.md): одно `AskQuestion` на раунд, вопросы только в форме, стоп и ждать ответ. Глубина гриллинга здесь всегда **light**. Стоп-форма гриллинга («Выполнить» / «Сделать план», `SwitchMode`) **не используется**.

## Вызов

```
/scenarios (название фичи|название сценария)
```

Скобки и пробелы вокруг `|` необязательны. Без глубины — light. `/scenarios deep` не углубляет продукт: это всё ещё границы схемы, просто второй раунд допустим сразу, если первый оставил дыру.

Если не хватает фичи или сценария — один вопрос в `AskQuestion`, только про недостающее имя. Гриллинг границ не начинать.

## Гриллинг границ

Перед вопросами быстро найти в репозитории код этого сценария (экраны, каналы, хранилища). В зеркале — 1–3 предложения: что понято и какие файлы похожи на источник правды. Решения и схемы в зеркале нет.

Один раунд, 2–3 вопроса. Угол только такой:

- где сценарий начинается и чем заканчивается
- какие входы входят, какие явно снаружи
- кто участники и где источник правды (файл, канал, хранилище)

Один вопрос — одна забота. Варианты конкретные, не «Да/Нет», если развилка не бинарная. Последний вариант каждого вопроса: `{ id: "simplify", label: "упростить или разбить на подвопросы" }`.

Не спрашивать сроки, раскатку, абьюз, «как бы я это написал». Не вываливать анкету. После формы ход закончен.

«упростить или разбить на подвопросы», «не понял», «вопрос непонятен», «варианты непонятны» — починить только этот вопрос по правилу **Unclear question** в grilling. Новых забот в том же ходе нет.

Второй раунд — только если ответ оставил границу дырявой или пользователь выбрал «Ещё уточнить». Покрытое заново не спрашивать.

## Стоп

Когда границы сценария ясны:

- В сообщении коротко: в сценарии / вне сценария / открытый риск. Без рекомендации в тексте и без «Дальше».
- В том же ходе одно `AskQuestion`. `prompt` — рекомендация, например: `Границы ясны, рекомендую собрать схему в docs/scenarios/<feature>/<scenario>.md`.
- Варианты по порядку: `{ id: "build", label: "Собрать схему" }`, `{ id: "more", label: "Ещё уточнить" }`. Без «упростить…» и без «Не собирать».
- Ждать клик. На `more` — ещё один светлый раунд. На `build` — следующий ход только пишет Markdown. `SwitchMode` не вызывать.

Путь в `prompt` — латинский kebab-case. Русские имена остаются заголовком файла, не именем файла.

## Сборка

Писать только после `build`.

1. Ещё раз прочитать код участников. Шаг, которого нет в коде или в ответах гриллинга, в схему не попадает.
2. Создать `docs/scenarios/<feature>/<scenario>.md`.
3. Если есть `docs/scenarios/README.md` — добавить строку. Если файла нет — создать оглавление из одной таблицы: фича, сценарий, файл.
4. Визуал и каркас Mermaid — [diagram.md](diagram.md). Эталон уже нарисованного сценария — раздел «Последовательности» в `docs/guides/api-stage-switch.md`.
5. Несколько независимых входов, которые гриллинг оставил внутри сценария, — несколько схем в одном файле, не одна простыня.

## Каркас файла

```markdown
# <Фича>: <Сценарий>

<2–4 предложения: кто запускает, чем заканчивается, когда новое состояние видно.>

## Границы

- В сценарии: …
- Вне сценария: …

## Участники

| Участник на схеме | Где в коде |
|---|---|

## Последовательность

<Абзац, что схема показывает. Потом один или несколько блоков mermaid с подзаголовком на каждый вход.>
```

Язык файла — русский. Имена методов, каналов и ключей хранилища — как в коде.
